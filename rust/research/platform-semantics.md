# Storage, locking and process semantics for a Rust rewrite

This memo records compatibility requirements for authorization, run history and task execution. It is research, not an implementation or dependency-selection decision. Metadata timestamps use America/Los_Angeles.

The source baseline is [`5fa7005813c99bc54ebef41447d4adb2aaa6c32a`](https://github.com/alexgorbatchev/cron-person-cli/tree/5fa7005813c99bc54ebef41447d4adb2aaa6c32a). Repository links below name files and line numbers at that baseline. Source inspection and the cited primary documentation establish the behavior described here; no Rust candidate was built, and no native platform or fault-injection test was executed for this memo. Candidate versions are explicit, auditable examples, not claims about the latest release or a selected minimum Rust version.

## Contracts that govern the port

| Area | Source-verified behavior | Consequence for a Rust port |
| --- | --- | --- |
| Authorization identity | Approval stores SHA-256 of the original `.cronrc` bytes; execution parses the same bytes that passed inspection. | Do not normalize line endings, serialize an AST, or reopen the path between authorization and environment construction. |
| Concurrent authorization changes | Writers lock a separate stable `.lock`, reload the latest store, clone it, then replace JSON. | Atomic replacement alone does not prevent a stale writer from restoring a revoked approval. |
| Run liveness | A fresh open of `run.lock` and a nonblocking OS lock probe determine liveness. | A PID, a timestamp, a missing heartbeat, or a lock filename is not proof of a live recorder. |
| Store persistence | Sync staged contents, close, rename, update memory, then sync the directory where supported. | A directory-sync error after rename is a visible commit with uncertain durability, not a failed precommit. |
| History persistence | Replace complete JSON files, but do not sync the staged metadata or directory. | Preserve visibility and error handling; do not advertise store-level power-loss durability for history. |
| Recording failures | Start, capture, finalization and pruning errors are reported without preventing an otherwise authorized task from executing. | Early error propagation from optional history work changes task behavior. |
| Process control | Unix process groups and sessions; Windows console groups plus a job assigned after process creation. | These mechanisms have different boundaries. A portable process API does not make their guarantees identical. |
| Detach | The foreground client can exit while a separate recorder keeps running and capturing output. | Killing children on owner drop, retaining terminal input, or treating broken foreground pipes as fatal breaks detach. |

## Authorization snapshots and identity

### Exact bytes, paths and read limits

- [`ComputeHash`](../../internal/cronrc/cronrc.go#L52) is SHA-256 of the provided bytes, encoded as 64 lowercase hexadecimal characters. [`ParseFile`](../../internal/cronrc/cronrc.go#L221) reads once and overrides the parser's hash with the original-byte hash. In contrast, [`Parse`](../../internal/cronrc/cronrc.go#L72) scans lines and hashes their newline-joined representation at line 119. That parser hash is not the approval identity: CRLF and a final newline can change the approved hash without changing parsed tasks.
- [`ReadFile`](../../internal/cronrc/read.go#L26) accepts at most 1 MiB, checks the opened descriptor's type, and rejects nonregular files. Its Unix open uses [`O_NONBLOCK`](../../internal/cronrc/open_unix.go#L12), so a FIFO cannot hang authorization before type inspection. Symlinks to regular files are accepted; inode identity is not stored. A replacement containing identical bytes retains the same approval identity.
- [`Allow`](../../internal/store/store.go#L246) resolves a lexical absolute directory, rejects CR/LF/NUL in schedulable paths, parses a file snapshot before acquiring the store writer lock, and saves that snapshot's raw hash and UTC approval time. A later file change is detected on inspection. Approval is not a lock against future file edits or revocation.
- [`Inspect`](../../internal/store/store.go#L361) reads `.cronrc` once, reloads authorization state, classifies the original bytes and returns those bytes. [`Runner.prepare`](../../internal/runner/runner.go#L202) parses that returned snapshot. [`InspectAll`](../../internal/store/store.go#L395) uses one store snapshot per operation, and [`Schedulable`](../../internal/store/store.go#L448) parses each returned file snapshot.
- [`classify`](../../internal/store/store.go#L498) distinguishes unauthorized, changed, missing and orphaned state. Read failures propagate except the explicit missing/nonregular classifications. Corrupt store JSON propagates rather than authorizing from a successfully parsed subset. The existing-store reload has an unusual directory-path branch that leaves cached records intact ([`reloadLocked`](../../internal/store/store.go#L116)); preserve or explicitly characterize that branch rather than claiming every unusable store path clears approvals.
- [`NewStore`](../../internal/store/store.go#L67) captures an absolute store path at construction. [`DefaultStorePath`](../../internal/store/store.go#L55) accepts an absolute `XDG_STATE_HOME`, otherwise uses the user's home plus `.local/state/cron-person/allowed.json`, including on Windows. Do not silently substitute a platform-directory crate's different default.

The current path identity is `filepath.Abs`/cleaned spelling, not filesystem canonicalization. Symlink resolution, Windows case folding, Unicode normalization or requiring the target to exist would change keys and history identities. [`Deny`](../../internal/store/store.go#L286) also removes stored keys whose absolute spelling resolves to the requested directory, including a hand-edited trailing separator. Rust `Path::canonicalize` is not an equivalent operation.

Candidate fit: [`sha2 = 0.10.9`](https://docs.rs/sha2/0.10.9/sha2/) provides `Sha256::digest(&[u8])` through `Digest`; explicitly encode lowercase hexadecimal. Keep the authorization snapshot as bytes, independent of any UTF-8 parser representation. On Unix, Rust 1.91.0 [`OpenOptionsExt::custom_flags`](https://doc.rust-lang.org/1.91.0/std/os/unix/fs/trait.OpenOptionsExt.html#tymethod.custom_flags) plus [`nix = 0.30.1`, `OFlag::O_NONBLOCK`](https://docs.rs/nix/0.30.1/nix/fcntl/struct.OFlag.html) is a concrete API combination for nonblocking open followed by descriptor metadata and a bounded read. This is an API fit, not a demonstrated parser or filesystem equivalence.

## OS-held locks

### Current lock protocol

[`LockPath`](../../internal/filelock/filelock.go#L18) opens or creates a read/write 0600 lock file, blocks for exclusivity, and returns a release function that explicitly unlocks before closing. Store mutation holds `<absolute-store>.lock` across reload and save ([`withFileLock`](../../internal/store/store.go#L102)); the store JSON itself is replaced, while its separate lock file is retained.

| Platform | Exact current operation | Error and ownership requirements |
| --- | --- | --- |
| Unix | [`flock(LOCK_EX)`](../../internal/filelock/lock_unix.go#L11), nonblocking `LOCK_EX \| LOCK_NB`, and `LOCK_UN`. | Only `EWOULDBLOCK` becomes the package's contention result. Other errors remain errors. |
| Windows | [`LockFileEx`](../../internal/filelock/lock_windows.go#L13), exclusive range starting at byte 0 with length 1; nonblocking adds `LOCKFILE_FAIL_IMMEDIATELY`. | Only `ERROR_LOCK_VIOLATION` becomes contention. `UnlockFileEx` uses the matching range. Files need not contain a byte to lock this range. |

The package's “process-scoped” description is an abstraction, not a precise Unix ownership model. Linux [`flock(2)`](https://man7.org/linux/man-pages/man2/flock.2.html) associates locks with an **open file description**. Duplicated descriptors and forked children share that lock; an explicit unlock through one duplicate affects it, and closing only one duplicate need not release it. Locks survive `exec` when the descriptor survives. A separately opened descriptor is a different lock owner even in the same process.

Consequently:

1. Keep the locking descriptor owned by the recorder/store operation. Do not pass it as child stdin/stdout/stderr, clear close-on-exec, or clone it into unrelated workers. The audited [Rust 1.91.0 Unix file-open implementation](https://github.com/rust-lang/rust/blob/1.91.0/library/std/src/sys/fs/unix.rs) adds `O_CLOEXEC`; custom descriptor plumbing still requires an inheritance audit and subprocess tests.
2. Probe liveness with a **fresh open**, not `File::try_clone`, `dup`, or a cached descriptor already holding the lock. Relocking a clone is explicitly unspecified in Rust's API and can deadlock. Accidentally unlocking a shared description can also release the real holder's lock.
3. Do not unlink or replace a live lock file. On Unix, [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html) leaves open references to the old inode valid. Removing/recreating the lock pathname can leave one writer holding the old inode while another locks the new one. Atomic JSON replacement must never become atomic lock-file replacement. A leftover *unlocked* lock file is harmless and does not need PID-based cleanup.
4. Lock behavior is filesystem-dependent. The Linux manual documents NFS/CIFS emulation and mount-dependent interactions, including differences from local advisory `flock`. Do not infer network-filesystem support from an ext4 test or substitute `fcntl` record locks without compatibility evidence.

Microsoft's [`LockFileEx` contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex) differs: a child's inherited handle does not grant access to the parent's locked region, and the OS can delay cleanup after close/process termination. This is why the store's release explicitly unlocks. History currently closes its lock at completion without explicitly unlocking ([`closeFiles`](../../internal/history/recording.go#L113)); the memo does not claim instantaneous Windows liveness changes on every close.

### Windows sharing is part of lock identity

The [Go 1.26.11 Windows open implementation](https://github.com/golang/go/blob/go1.26.11/src/syscall/syscall_windows.go) uses `FILE_SHARE_READ | FILE_SHARE_WRITE`, excluding deletion. Rust 1.91.0's [`OpenOptionsExt::share_mode`](https://doc.rust-lang.org/1.91.0/std/os/windows/fs/trait.OpenOptionsExt.html#tymethod.share_mode) defaults to **read, write and delete** sharing. Leaving that default on lock files would permit a namespace operation that the Go holder normally prevents, risking the same split-lock problem after replacement.

Candidate preservation: explicitly set `share_mode(FILE_SHARE_READ | FILE_SHARE_WRITE)` for stable lock files, keep handles noninheritable, and test rename/delete attempts while a Go or Rust holder is active. Metadata reader sharing is a separate choice: increasing it can reduce replacement contention but changes cross-version behavior and must not leak into lock-file construction.

### Rust lock API fit

Rust 1.91.0 [`File::lock`, `try_lock`, `unlock`](https://doc.rust-lang.org/1.91.0/std/fs/struct.File.html#method.lock) were stabilized in 1.89.0. The documented current implementation uses Unix `flock` and Windows `LockFileEx`. [`TryLockError`](https://doc.rust-lang.org/1.91.0/std/fs/enum.TryLockError.html) distinguishes `WouldBlock` from `Error(io::Error)`; only the former is liveness contention. Permission, bad-handle and unsupported-operation errors must not become “running” or “interrupted.”

The [versioned Windows std implementation](https://github.com/rust-lang/rust/blob/1.91.0/library/std/src/sys/fs/windows.rs) locks a much larger range beginning at zero than Go's one-byte range. Those exclusive ranges overlap, so the APIs are candidates for Go/Rust contention interoperability; this is source-based reasoning, not an executed interoperability result. Exact one-byte operations can instead use `windows-sys = 0.61.2` with [`LockFileEx`](https://docs.rs/windows-sys/0.61.2/windows_sys/Win32/Storage/FileSystem/fn.LockFileEx.html) and [`UnlockFileEx`](https://docs.rs/windows-sys/0.61.2/windows_sys/Win32/Storage/FileSystem/fn.UnlockFileEx.html), retaining matching `OVERLAPPED`/range and error handling.

Do not add `fs2` solely to obtain locking if the eventual minimum Rust version permits std locks. No alternative crate has been established as more compatible here. Explicit unlock and close/error ownership still need a small platform boundary; an RAII destructor is not a place to return a close failure.

## Durable JSON and replacement

### Authorization store transaction

[`saveRecordsLocked`](../../internal/store/store.go#L142) has these observable phases while holding the stable writer lock:

1. Reload current JSON under the lock before changing the cloned map; save a directory-sorted array of records, using two-space JSON indentation. Record fields are `dir`, `path`, `hash`, `allowed_at` ([schema](../../internal/store/store.go#L36)); repeated directory keys in an input array use the last record during load.
2. Remove only recognized abandoned staging files. Create a sibling 0600 temporary file with the store basename plus `.<random>.tmp`; write all encoded bytes, sync the file, and close it. Join write, sync and close failures; remove the owned temporary file on failure.
3. Rename the sibling over the destination. Rename failure removes the owned temporary and leaves the previous in-memory map unchanged.
4. Once rename succeeds, update memory to the committed records, then sync the parent directory. A directory-sync failure is returned **after** memory follows the now-visible file. Rolling memory back would contradict disk and can reintroduce incorrect approval state.

[`createDirDurably`](../../internal/store/store.go#L187) also flushes the parent entries of newly created directories. Unix [`syncDir`](../../internal/store/sync_unix.go#L14) opens the directory and syncs it, suppressing only `EINVAL`, `ENOTSUP` and `EOPNOTSUPP`; other sync errors and a close failure remain visible. [`syncDir` on Windows](../../internal/store/sync_windows.go#L3) is a no-op. Its current contract leaves rename survival through power loss to the filesystem.

Linux [`fsync(2)`](https://man7.org/linux/man-pages/man2/fsync.2.html) explicitly distinguishes file-content syncing from syncing the containing directory entry. [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html) gives atomic replacement visibility on the documented filesystem boundary, not durable storage by itself. A process killed between phases is not the same test as losing power or volatile device caches.

On macOS, both audited runtimes use `F_FULLFSYNC`, but they differ on fallback: [Go 1.26.11](https://github.com/golang/go/blob/go1.26.11/src/internal/poll/fd_fsync_darwin.go) retries ordinary `fsync` when `F_FULLFSYNC` returns `ENOTSUP`; [Rust 1.91.0](https://github.com/rust-lang/rust/blob/1.91.0/library/std/src/sys/fs/unix.rs) directly returns the `F_FULLFSYNC` result. Apple's [primary `fsync` documentation](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html) explains why the stronger operation exists. A direct `sync_all()?` can therefore reject a store write that Go permits on a filesystem without full-sync support. Preserve the fallback at the platform boundary or obtain an explicit behavior decision; do not broadly suppress regular-file sync errors.

### Temporary-file ownership and cleanup

[`removeStaleTempFilesLocked`](../../internal/store/store.go#L224) recognizes only `<store-basename>.<nonempty decimal digits>.tmp`. Under the writer lock, every matching file created by this protocol is abandoned, so removal is best effort. Such files are never read as authorization. Other `.tmp` files remain untouched.

[`tempfile = 3.23.0`, `NamedTempFile::new_in` and `persist`](https://docs.rs/tempfile/3.23.0/tempfile/struct.NamedTempFile.html#method.persist) are candidates for same-directory staging and replacement. `persist` documents replacement and returns the owned temporary on failure, but **does not sync contents or the directory**. Its default random filenames do not implement the Go decimal-only ownership matcher. A port needs a deliberately compatible naming protocol, or an explicitly owned new staging namespace and migration cleanup policy; generic deletion of temporary files is not equivalent. Destructor cleanup also does not run after an abrupt process death.

Rust [`File`](https://doc.rust-lang.org/1.91.0/std/fs/struct.File.html) ignores close errors in `Drop`. `write_all`, `sync_all` and an explicit result-carrying commit boundary are necessary, but `drop(file)` cannot reproduce Go's fallible `Close` result. Any platform-specific close wrapper must avoid retrying a Unix close after a potentially released/reused descriptor. This remains an implementation design requirement, not solved merely by selecting `tempfile`.

### History JSON has a weaker persistence contract

[`history.writeJSON`](../../internal/history/history.go#L501) writes and closes a sibling temporary, then replaces the destination. It has **no file or directory sync**. Unix [`replaceFile`](../../internal/history/replace_unix.go#L8) uses `os.Rename`. Windows [`replaceFile`](../../internal/history/replace_windows.go#L13) makes at most 50 attempts, sleeping 10 ms after `ERROR_ACCESS_DENIED` or `ERROR_SHARING_VIOLATION`; other results return immediately. This handles a Go reader temporarily opening the target without deletion sharing. It is not an unbounded permission-error retry.

Rust 1.91.0 [`fs::rename`](https://doc.rust-lang.org/1.91.0/std/fs/fn.rename.html) documents platform-specific replacement behavior. The [tempfile 3.23.0 Windows backend](https://docs.rs/crate/tempfile/3.23.0/source/src/file/imp/windows.rs) clears the temporary attribute and calls `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING`; it does not add `MOVEFILE_WRITE_THROUGH`. Microsoft's [`MoveFileExW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) and [`FlushFileBuffers`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers) contracts must be assessed separately from Unix rename/fsync. No source here establishes a universal Windows crash-durable atomic transaction on every supported filesystem.

Candidate serialization: [`serde = 1.0.228`](https://docs.rs/serde/1.0.228/serde/) derives plus [`serde_json = 1.0.145`, `from_slice`](https://docs.rs/serde_json/1.0.145/serde_json/fn.from_slice.html) and [`to_vec_pretty`](https://docs.rs/serde_json/1.0.145/serde_json/fn.to_vec_pretty.html). These provide byte-based JSON decoding and pretty encoding, not automatic Go schema equivalence. Test absent fields, `null` versus empty arrays, field omission, UTC RFC3339 fractional precision, HTML escaping and unknown fields against Go fixtures. Stable authorization hashes are of `.cronrc` bytes, never of serialized store JSON. No timestamp or random-ID crate is selected in this memo.

## History recording and liveness

### Layout and lifecycle

[`DirForStore`](../../internal/history/history.go#L111) places history in `runs` beside the authorization store. Stores with different filenames in the same parent directory consequently share that history root. [`TaskID`](../../internal/history/history.go#L104) is the first six bytes of SHA-256 of `dir + NUL + command`, encoded as 12 lowercase hex digits. It must not become Rust's randomized `Hash` output. [`newRunID`](../../internal/history/history.go#L481) uses UTC microsecond timestamp format `20060102T150405.000000Z` plus a hyphen and four random bytes in hexadecimal.

The layout is `<runs>/<task-id>/<run-id>/{meta.json,output.log,run.lock}` with `task.json` in the task directory. Directories use 0700 and newly created output/lock files 0600. These Unix mode values are not a Windows ACL guarantee. The [`Run` schema](../../internal/history/history.go#L69) omits unfinished `finished_at`, absent `exit_code`, empty errors/warnings, and false `truncated`.

[`Start`](../../internal/history/recording.go#L60) updates task metadata, creates a unique run directory, exclusively creates and locks `run.lock`, exclusively creates output, then writes running metadata last. Failed setup closes owned handles and removes the owned run directory. [`Recording.close`](../../internal/history/recording.go#L166) flushes partial output, writes final metadata, closes output, and releases the lock last. Final status is succeeded, failed or blocked; a signaled task has no numeric history exit code. A metadata-write failure can leave running metadata after the lock releases, which is subsequently read as interrupted.

[`readRun`](../../internal/history/history.go#L429) reads metadata, and if it says running, probes the lock. After observing an unlocked run it **rereads metadata** before deriving interrupted status, avoiding a stale-running read racing a successful completion. Interrupted is a read-time status only, without an invented exit code or finish time. [`locked`](../../internal/history/history.go#L454) opens the existing lock read/write without creation; a missing lock means unlocked, actual contention means live, and other errors propagate. A successful probe closes its own freshly opened file.

[`Follow`](../../internal/history/history.go#L368) probes before the last output copy, then rereads final metadata after release so it does not miss the last bytes. [`Prune`](../../internal/history/history.go#L252) preserves held locks and the latest run of each task; incomplete runs younger than the one-minute creation grace are protected before their lock exists. Age/byte retention targets can therefore remain exceeded. Foreign directories are ignored, and interrupted runs can eventually be pruned.

### Execution must survive recording failure

[`Runner.Exec`](../../internal/runner/runner.go#L66) attempts history setup **before** authorization preparation so refused runs can be recorded. Setup failure is retained while task authorization and execution continue. Refusal records `blocked` where recording exists. Capture/finalization errors and pruning errors are joined with the task result after execution. A history-only error may make the CLI return failure after a successful task; independence means task execution is preserved, not that observability errors disappear.

[`runRecordedTask`](../../cmd/cron-person/exec.go#L68) replaces unreadable configuration with defaults, records a warning, and prints it for manual runs. The configuration read error itself does not fail a successful cron run. A later failure to report the run ID is returned after execution. Preconditions such as an unusable authorization store or failure to resolve an absolute target still prevent execution; this is not a promise to execute without authorization.

[`streamWriter.Write`](../../internal/history/recording.go#L225) always reports the full accepted input length and no error, retaining capture failure for finalization. Output records have `[out] ` or `[err] ` prefixes and split at 64 KiB of bytes, including unterminated output. One mutex serializes observed record writes; it cannot reconstruct the true production order of two independent pipes. [`writeRecordLocked`](../../internal/history/recording.go#L195) stops storing complete records when the byte cap would be exceeded, emits one truncation notice, and continues consuming task output. The notice can itself put stored size over the configured cap. Preserve byte handling, including invalid UTF-8.

[`passthroughWriter`](../../internal/runner/runner.go#L177) discards caller-output writes after their first error, allowing capture to continue after detach. The recorder observes SIGPIPE instead of terminating ([`exec.go`](../../cmd/cron-person/exec.go#L89)). Rust [`println!`](https://doc.rust-lang.org/1.91.0/std/macro.println.html) panics on output failure; direct fallible writes with the same best-effort policy are required on that path. Do not propagate a broken foreground pipe into the task's recording writer or stop draining a child whose capture disk is full.

## Processes, sessions and terminal attachment

### Execution and cancellation

[`Runner.prepare`](../../internal/runner/runner.go#L202) constructs a shell command from the authorized snapshot. Shell selection uses ambient `SHELL`, then `/bin/sh` if empty, with a nonempty `.cronrc` `SHELL` taking precedence. It passes `-c` and the **entire command as one argument**, sets the working directory, overlays process environment, `.cronrc` environment and `ExtraEnv`, then fixes `PWD`, `CRON_PERSON_DIR` and `CRON_PERSON_CRONRC`. Windows does not silently substitute `cmd.exe`; the native tests use an available POSIX-compatible shell.

[`runGroup`](../../internal/runner/runner.go#L131) configures a process group, starts the task, attaches the platform group owner, waits, stops its escalation timer and closes the owner. A group-attachment failure kills and waits for the direct child. Cancellation before a group owner is available falls back to killing the direct child. The default grace is 10 seconds and bounds both graceful cancellation and inherited-output draining. An `exec.ErrWaitDelay` from output staying open becomes a warning and a successful task outcome ([`Exec`](../../internal/runner/runner.go#L112)).

| Platform | Verified current mechanism | Boundary to retain or characterize |
| --- | --- | --- |
| Unix task | [`Setpgid: true`](../../internal/runner/process_unix.go#L18); send SIGTERM to negative task PID, then SIGKILL after grace. ESRCH becomes process-done. | The process group covers descendants that remain in it, not processes that deliberately move to another group/session. |
| Unix recorder | [`Setsid: true`](../../cmd/cron-person/attach_unix.go#L12); foreground termination sends SIGTERM to the recorder. | Recorder owns task cancellation and final recording. Killing the task directly bypasses that owner. |
| Windows task | [`CREATE_NEW_PROCESS_GROUP`](../../internal/runner/process_windows.go#L22); after start, create job, open process with `PROCESS_SET_QUOTA \| PROCESS_TERMINATE`, assign it. | A descendant created before assignment is explicitly outside the source's guarantee. Closing the job handle alone is not configured to kill the job. |
| Windows cancellation | [`GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, pid)`](../../internal/runner/process_windows.go#L44), then `TerminateJobObject`; if console delivery fails, terminate job immediately. | Ctrl+Break requires the sender/recipients to share a console. A job is a separate membership/termination mechanism. |
| Windows recorder | [`CREATE_NEW_PROCESS_GROUP`](../../cmd/cron-person/attach_windows.go#L14); foreground termination sends Ctrl+Break. | This is not a detached session or `DETACHED_PROCESS`; the recorder interrupt helper has no headless fallback of its own. |

Primary semantics: Unix [`setsid(2)`](https://man7.org/linux/man-pages/man2/setsid.2.html) creates a session/process group without a controlling terminal; [`kill(2)`](https://man7.org/linux/man-pages/man2/kill.2.html) explains negative-PID group signaling. Microsoft documents [console event delivery](https://learn.microsoft.com/en-us/windows/console/generateconsolectrlevent), [creation flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags), [job inheritance and breakaway](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), and [job-assignment requirements](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject). Nested-job support differs on older Windows; a host that already places the CLI in a job needs native coverage.

Two limits need characterization before stronger rewrite promises: if the Unix group leader exits and a descendant closes its output but ignores termination, `Wait` can return and the source stops the escalation timer; and Windows job assignment has a post-start gap. These are source-supported risk scenarios, not reproduced defects in this research. Suspended Windows creation followed by assignment/resume could address the latter, but that is an architectural candidate needing startup/error-path design, not established parity. Adding `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` would also change behavior and must not be an incidental crate default.

### Foreground attach/detach

[`runAttached`](../../cmd/cron-person/attach.go#L31) reexecutes the current binary as the recorder with absolute store/config paths, manual trigger, a run-ID exchange file, absolute task directory and a single command argument. This is the ownership boundary that lets capture survive detaching the client.

- [`attachedRun.run`](../../cmd/cron-person/attach.go#L88) connects ordinary pipes, closes unused pipe ends after spawn, relays stdout/stderr concurrently with serialized caller writes, and waits for the recorder separately. It does not allocate a PTY or put the terminal in raw mode.
- Noninteractive file input can be passed directly. Terminal input and arbitrary readers are relayed through a pipe so the detached task does not retain the terminal. Interactive input forwarding has a bounded 64-chunk queue and a separate writer; a recorder that closes stdin does not make that writer stop draining the queue ([`forwardInput`](../../cmd/cron-person/attach.go#L271)).
- On interactive Ctrl+C, the first signal prompts `Also terminate the task? [y/N]`. `y`/`yes` or a second interrupt requests termination. Any other response, empty input or EOF while prompting detaches successfully; noninteractive interrupt, SIGTERM and SIGHUP terminate without prompting ([event loop](../../cmd/cron-person/attach.go#L163)).
- [`readInput`](../../cmd/cron-person/attach.go#L241) permits another terminal read after Ctrl+D and ends after two consecutive EOFs. [`isTerminal`](../../cmd/cron-person/attach.go#L294) recognizes only a file handle accepted by `x/term`.
- Detach closes the foreground relay ends and input forwarding, returns success and reports the run ID if available ([`detached`](../../cmd/cron-person/attach.go#L210)). The recorder must keep capturing after those output pipes close. [`reportRunID`](../../cmd/cron-person/exec.go#L118) opens an existing file without creation; if the foreground already removed it, the recorder does not recreate it.
- [`recorderResult`](../../cmd/cron-person/attach.go#L227) forwards a positive recorder exit status without printing the already-relayed error twice. [`exitCode`](../../cmd/cron-person/main.go#L49) preserves task exit codes through joined errors and maps Unix signals to `128 + signal`; the history record still omits a numeric code for signal termination.

Do not infer survival of Windows console closure from “new process group.” The current source and simulated-signal tests do not establish that guarantee. Likewise, Go attachment tests mostly drive channels/readers; that is useful control-flow coverage, not proof of real terminal line discipline or every console host.

## Platform evidence still needed before implementation acceptance

The release targets are Linux, macOS and Windows on amd64/arm64 ([release configuration](../../.goreleaser.yml)); the inspected [CI workflow](../../.github/workflows/ci.yml) executes on Ubuntu. A GOOS vulnerability scan or cross-compiled binary is not a native locking, console or rename test.

Acceptance therefore needs native Linux/macOS/Windows results for the rows above, with filesystem, architecture, OS and shell/console prerequisites recorded. Especially unresolved are Go/Rust mixed-process lock interoperability, Windows replacement under Go readers, Darwin full-sync fallback, actual terminal event handling, Windows headless recorder cancellation, and cancellation after early leader exit. Unsupported network/filesystem combinations must be stated at their actual evidence boundary. A documented API is candidate fit; only the relevant process and failure-path tests establish behavioral parity.
